# Dynamic Model and Tool Routing

## Principle

Route by required capability first, then quality risk, latency, and token cost. Names, prices, context limits, availability, and bridge tools change; discover them in the executing host at runtime and never invent them.

## Capability classes

- **Orchestrator/reviewer:** strongest available reasoning and cross-domain integration for architecture, contested decisions, final review, and recovery.
- **Volume worker:** cheapest reliable coding/research model for well-specified, testable, isolated jobs.
- **Visual worker:** model that can inspect screenshots, frames, diagrams, materials, UI, and generated variants.
- **Creative generator:** image, video, audio, voice, music, or 3D service accessed through an available tool; generation is not acceptance.
- **Specialist bridge:** another model family or coding host used for a genuinely different strength, independent critique, or rescue after evidence of failure.

## Routing loop

1. Inventory callable models, tools, bridges, context boundaries, and costs from current host state or official sources.
2. Label each job by required capabilities, risk, reversibility, evaluation clarity, and context size.
3. Start with the least expensive option that plausibly clears the acceptance bar.
4. Escalate only after a failed test, ambiguous architecture decision, repeated repair, security/release risk, or demonstrated quality deficit.
5. Use test-time compute where another candidate, critique, or simulation has positive expected value. Stop when evidence converges.
6. Record routing decisions and observed failures so later packets improve.

## Context economics

Use fresh independent sessions for coherent jobs. Pass a Goal Packet, not accumulated chat. Summarize results into commits, evidence, and knowledge packets. Do not keep expensive orchestrators doing bulk implementation that a lower-cost worker can perform safely.

Parallel workers must own non-overlapping surfaces. More agents are not a quality metric.

## Cross-model collaboration

When the host exposes session messaging or model bridges, permit the orchestrator to call them. Verify the actual interface first. A bridge is optional and must have a local fallback: an isolated task, committed packet, or human-readable handoff.

Do not hard-code fashionable model names into generated Goals unless the user explicitly pins them and the executing host confirms availability. Do not purchase fast/priority tiers or new subscriptions without approval.
